# Add individual apps to a browser home screen

By default, hold an app in Apps or New desk, or hold and release a one-app desk without dragging. Miguel’s family (Obsidian, Obsidian Light, Landscapes) carries the optional `miguel/arrange-download` tweak: hold a desk to arrange/reorder/close; tap its download button to open installation. Home, system and multi-app desks have no download button. Turning the tweak off restores hold-to-offer without changing skins. The package declares layout + navigation capabilities and calls `api.overview.use({hold:"arrange", appAction:"home-screen", appHold:false})`. The host validates options and owns teardown; the shared phone-shell adapter owns rendering/input, with no package-ID checks. Replacement, opt-out and stale handles restore the default mode. Desktop has no touch overview adapter and stays unchanged. The current AGENTS tweaks contract supersedes putting new behavior in skin scripts. The native Android `wizardHomeScreenPort` branch is unchanged. Without the native bridge, web/PWA clients get a manual two-step guide:

1. **Open this link in Safari / Chrome / your browser** — one **Copy link** button and a wrapped, selectable address. Copy, manually open the browser, and paste into its address bar. iPhone/iPad (including desktop-UA touch iPad) uses Safari; Android uses Chrome; other clients use generic browser wording.
2. **Save to Home Screen** — iOS: Share → Add to Home Screen → Add. Android: Chrome ⋮ menu → Add to Home screen / Install app. Other browsers: their install/home-screen menu, if available.

The displayed and copied link is exactly the validated registered `app.url` resolved against the current origin (Wisdom is `/wisdom/`, not a guessed `/apps/wisdom/` or an install intermediary). The existing same-origin, frontend-path and ID checks remain required. Denied clipboard access selects that same URL for manual copying. No new-tab escape or silent-install promise is made.

## App-level identity on the app's own page

For supported pages without their own manifest, saving a direct app link supplies app-level PWA metadata: the registry name (e.g. **Morning Report**, not the report's page title), the app's house sigil, and launch at the app root (not the report/day being read).

- **Shared injection point:** `/wizard-os-home/core/app-client.js` (the WizardApp SDK that app pages load from the shell origin) loads `core/app-identity.js` in top-level documents only (never inside the shell frame). Apps are served at their own paths by Tailscale Serve straight to their containers, so the shell nginx is not in front of them; the SDK is the one shared layer they all run.
- `app-identity.js` uses the first path segment only as a lookup key and adds, in `<head>`: `<link rel=manifest href=/wizard-os-home/install/at/<segment>.webmanifest>`, `apple-touch-icon` (180px), `apple-mobile-web-app-title` / `application-name` (registry name), `apple-mobile-web-app-capable` and `mobile-web-app-capable`.
- **Manifest:** served by the same read-only `packaging/app-install.py` responder. It matches only a registered app whose validated same-origin `url` path is exactly `/<segment>/` (fresh authenticated registry read, same URL safety rules, redirects not followed, 401/403 passed through, otherwise 503). `id` = `scope` = app root path, `start_url` = registered url (path, query and fragment), `name`/`short_name` = registry name, `display: standalone`, icons 192/512/180 PNG from `/wizard-os-home/install-icons/`. Unregistered → 404, and the client removes its speculative link. Callers cannot supply names, URLs or icons.
- **Precedence:** an app's own `<link rel=manifest>` wins (e.g. Music, Files). No second manifest is added and no launch redirect happens. Existing `apple-touch-icon`/`apple-mobile-web-app-*` tags are never replaced, only filled in when missing.
- **Deep URLs:** Chrome/Android uses the manifest `start_url`, so the installed app opens at the root whatever page was open. iOS Safari ignores `start_url` and saves the *current* URL. To handle that, the first load of an iOS home-screen launch (`navigator.standalone`, once per launch via `sessionStorage`) `location.replace`s to the registered root. Later in-app navigation is untouched. Not applied in Chrome, where installed windows may legitimately open in-scope deep links. The guide already copies the registered root URL.
- **Icons:** `node tools/build-install-icons.cjs --registry <saved /wizard/v1/apps JSON>` renders every house sigil plus the launcher's letter-disc fallback for registered apps without a house entry, at 512 (`<id>.png`), 192 (`<id>-192.png`) and 180 (`<id>-180.png`).
- **Coverage:** every app page that loads the shared `app-client.js`. App pages that don't (as of this change: Profiles, Claude, ChatGPT, Tinfoil, SimpleFIN, Cloudflare, Shopping's vendored copy, File Browser) keep their previous behavior until they load `/wizard-os-home/core/app-client.js` or `/wizard-os-home/core/app-identity.js`. That is a one-line, app-side change; the hello-wizard template does not include the SDK yet.
- **QA:** `QA_OUT=… QA_ORIGIN=https://<host>:8444 QA_RESOLVE='MAP <host> <ip>' node qa-app-home-identity.cjs` checks real app pages at their real paths in Chromium. Chromium checks are not physical Safari proof.

**Remaining direct-link limitations:** an app that ships its own manifest owns its identity. Files/File Browser keep their existing manifest/frontend behavior; this does not certify their name/icon or app-root launch. Monarch requires its frontend to load the shared SDK/identity script; generating its icon alone does not integrate that frontend. No app-side SDK adoption is included here. Native shortcuts keep their existing separate session contract.

Installation still needs browser/OS confirmation, HTTPS (or localhost for development), and access to the Wizard. A web page cannot silently pin icons or reliably query whether an iOS icon already exists. Authentication may need repeating in the installed app on platforms with separate storage.

## Compatibility install endpoints (not used by the new guide)

`/wizard-os-home/install/<registered-id>/` remains a server-rendered compatibility install document. Its stable, same-origin `manifest.webmanifest` has an app-specific `id`, `name`, icon, `scope` and `start_url`. No blob/data manifest, query-supplied display names, arbitrary navigation destination, or install-state localStorage flag is used. Names are bounded/escaped; IDs and frontend routes are validated against a fresh, authenticated `/wizard/v1/apps` response. Removed apps fail closed. Registry unavailability is a retryable 503, not a stale install offer. Registry redirects are not followed and identity headers are forwarded, never invented.

Each app has its own path scope. The manifest starts at `?launch=1`; Safari reopening the saved canonical URL is recognized through standalone mode. The install guide does **not** auto-launch in an ordinary browser. An explicit `?install=1` handoff can show the guide inside an existing installed PWA; it removes that marker before Safari saves the page. The installed document contains one full-height frame hosting the existing `?app-session=<id>` entry; that session still owns the app frame, Back, appearance and reading state. The outer frame preserves the app's manifest identity and scope instead of navigating into the shared Wizard workspace URL.

Known house apps use 512px opaque PNGs generated from the existing `WizSigil` artwork. Regenerate with `node tools/build-install-icons.cjs` and the repo's `QA_PLAYWRIGHT` override when sigils change. Unrecognized/custom apps use the Wizard mark (never a remote/untrusted icon URL); their names and install identities remain separate.

The shell previously served only static files. Packaging now includes a small Python-stdlib **read-only** responder over a private Unix socket, supervised alongside nginx. Either process exiting terminates the other so container restart policy can recover the pair. No extra host port, app registry write, external sidecar, or owner configuration is required. nginx proxies only the install namespace to it; everything else retains its existing routing. Docker's existing `stamp-assets.sh` versions the install template's JS/CSS as well as changed shell assets. The existing service worker is network-only and caches no private pages or registry responses.

A static-only development server cannot serve these per-app manifests. Use the packaged container, or an explicit test responder; do not replace them with blob manifests.

## Verification

- `QA_OUT=<private-receipts> QA_ORIGIN=<staged-or-live-origin> node qa-ios-install-sheet.cjs`: trusted touch hold/tap on the actual shell, iPhone/Android browser/PWA, desktop-UA iPad and generic browser, real browser clipboard write/readback, deterministic denial, tap/hold selection, geometry and Back. `QA_RESOLVE='MAP hostname address'` supports private host resolver overrides. No installation or production-data mutation is performed; launcher state is in an isolated browser context.
- Interaction investigation: the old Copy handler did receive trusted touch in Chromium; the `freshPress` guard did **not** reproduce a dropped copy tap there. The old field did inherit `-webkit-user-select:none` from the shell, however. The selectable control now explicitly restores text selection/callout, and its click is exempt from the action guard after selection-related pointer cancellation. Buttons still require a fresh press. This is not evidence about the owner's Safari event stream.
- The compatibility install documents/manifests remain unchanged. The new shell guide never links to them. Registry URL query/hash components, if present, are preserved.
- `npm test`: includes the Python HTTP contract (`tests/app_install_test.py`) and existing native pin/desk/gesture/session tests.
- `QA_OUT=<private-receipts> QA_ORIGIN=<isolated-container> node qa-pwa-app-install.cjs`: real Chromium with Android/iPhone user agents, standalone simulation, manifest parsing/installability diagnostics, native and prompt handler fixtures, clipboard denial, trusted touch hold, ordinary tap/Back, isolated session/reload and mobile geometry. Run against `tools/qa-install-fixture.py` as the container's upstream so no production data is read or changed.
- For the original source negative control, serve its `web/` with `QA_WEB_ROOT=<baseline-web> QA_FIXTURE_PORT=<port> python3 tools/qa-install-fixture.py`, then run the browser suite with `QA_BASELINE=1` against that loopback origin. It verifies that browser hold was inert and the per-app manifest route was absent.
- `qa-home-screen-apps.cjs` remains the separate Thales/actual-frontend suite; its browser fallback assertion is updated. That suite is not replaced by synthetic app content.

These checks are **not physical iPhone/Android installation, OS home-icon deduplication, Recents, process-death, or actual Safari engine proof**. The owner has separately tested and approved supported-app name/icon/root launch and arrange/download on a physical iPhone in the existing personal release; that is not proof for every app or this new upstream tweak adapter. do not claim them from emulation. App-specific sites can still require a network connection. This feature does not add offline app storage or change native shortcut identity.

For read-only post-deploy verification run the same `qa-ios-install-sheet.cjs` against the live HTTPS origin, without `QA_WEB_ROOT`. It reads Wisdom from the actual loaded registry and records registered/direct URLs. Set `QA_WEB_ROOT=<candidate>/web` only for pre-deploy candidate-overlay QA; receipts explicitly label it. All non-read network requests are blocked in the isolated context. Docker asset stamping versions changed JS/CSS; the network-only worker needs no cache migration.
