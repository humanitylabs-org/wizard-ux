# Recorder recovery at the interface Reload guard

## Component decision
- **REUSE** `WizAppCapture` durable custody, microphone lock and `recover` lifecycle; `WizAppServices.update.reloadPlan`; `WizWebUpdate.reload/go`.
- **EXTEND** these owners with a tap-only, fail-closed ownership refresh and a proven-durable stopped-custody predicate. No replacement recorder, second reload guard, audio deletion or hold timeout.
- **NEW** regression fixtures only. `qa-closed-shell.cjs` adopts the existing closed synthetic shell fence from the live unread-badge acceptance (599ff269); the Recorder runner adds no owner/network fallback.

## Verified lineage and limits
Serving shell discovery on 4 November: the service's `WIZARD_UX_DIR` selected immutable release `599ff2694806235759738c4a1a2c5e2011dfd6e4`. Resolve the actual configured path before each promotion.
Serving Recorder frontend is the immutable `7b4a3d1-owner-876c5c8b9a38-nodiar/adoptions/mizel-live/web/app.js` release (source only inspected). No meeting API, private DB, audio, title, transcript or agent home was read.

The screenshot's toast is emitted by `web/core/web-update.js:reload`, where either the host is busy or a non-armable hold blocks. It cannot identify the handset's in-memory owner. No claim is made that server inspection proves the handset state.

The serving Recorder has a concrete failed-start lifecycle leak: `beginRecording` catches Start errors, clears `state.rec.engine`, then unconditionally calls `startPillClock`; that function acquires `Mizel recording`. `stopRecording` returns immediately in error phase, and normal `endRecSession` releases the hold only after a successful save. The shell's existing broad capture-name matcher already recognizes both `Mizel recording` and `Mizel capture or durable task save`; a label mismatch is **not** the cause.

Separately, the old Reload path judges a synchronous ownership snapshot. Abandoned native ownership is refreshed by capture recovery, not by Reload, so a stale owner can keep the banner held. The old `go` also waits 900 ms after the click without checking whether recording/work began during that animation.

## Safe behavior
1. Real active browser capture, stopping/input-memory state, mic preparations/loans and unknown native owners still block. Android's existing positive native-survival path stays intact.
2. With no in-page active session or warm preparation, a tapped Reload paints `Checking recorder…`, uses the existing locked recovery, then judges a fresh whole-shell plan. A 15-second UI wait bound restores retryability; it never cancels capture or expires data/holds.
3. App-owned holds are never bypassed, even when shared capture storage is durable. A companion Recorder source correction acquires its hold before Start, retains late-start sessions/queued audio on errors without cancellation, and releases only its own failed-start hold after positive empty app-memory + current/pending-custody checks. Error Stop can dismiss that positively empty state; retained audio keeps the normal Stop/Retry/readback/ack path. Notes, unrelated work, unknown custody and all other app holds remain blocked.
4. Every final reload checks the host + app/capture predicate after its animation and after native backup flushing. Preparation is non-destructive; frame removal is a separate synchronous commit after the final predicate and host persistence hooks, adjacent to reload. The kept native take must still be the exact take that was prepared. Aborting leaves the frame, holds and observers intact.

## Bootstrap / owner safety
An already loaded handset still runs the old guard until it obtains new JS. Deployment does **not** inject a bypass into a live page. First finish/save any actual recording using its owning Recorder/voice controls. If the old Reload is still blocked, opening Recorder can run its existing shared-capture reattach/recovery path. Do not force-stop, clear browser storage, force-close the APK, or discard an error-state take. If that still does not free Reload, a handset control-only owner inspection/readiness confirmation is required before a one-time document reload; the server alone cannot prove that an in-page buffer is empty.

No Recorder service restart or backend migration is needed for the shell patch. The actual failed-Start lifecycle repair is in the companion `wizard-recorder` branch `fix/recorder-start-reload-20261104`, head `7b0a091c1e16b5e8a1b0ddf108050d507ebed691`; it is not implemented by a shell exception. Its predecessor `f78e8a7995f145f876bcd93e7787968a0e7c7a6a` preserves the effective serving code/style overlays. The functional app diff is `adoptions/mizel-live/web/app.js`, its production-controller test and the owning `RECORDING-LIFECYCLE.md` contract. This live-preserving branch is an acceptance input, not permission to overwrite a newer installed app with its full old tree. Deployment must preserve all currently serving unrelated features and be coordinated against the live release immediately before activation.

### Deferred Reload consent
Deferred Reload is opt-in only for a positively identified live engine (`waitForEnd`) or the existing safely kept native meeting's own save. A capture-shaped blocker alone is not a recording: native uncertainty, recovery errors, unresolved custody, warm preparations and microphone loans never arm it. A resolved unsafe/absent ownership check shows the retryable error just like a rejection, and later native recovery or a fresh Start cannot consume that failed tap. Losing positive custody cancels an already armed wait.

## r4 acceptance failure and focused r5 correction
The r4 candidate browser stopped at `phone: real browser capture`: after a null native status, recovery resolved with `safe:false`, but Reload ignored that result; `reloadPlan.recording` treated every capture blocker as a real recording and armed a deferred Reload. Removing the failing bridge emitted recovery state and consumed that arm before fresh Start. The deterministic production-body regression reproduces the false arm for null, malformed, missing and throwing status and verifies that the corrected path remains unarmed through recovery, fresh capture and periodic/event checks; a new explicit recording-time tap still reloads exactly once on safe release.

The browser runner now asserts unarmed state on each status error and after fresh Start. Its Stop evidence goes synchronously through one exact closed synthetic route to a disposable loopback sink; it receives the genuine wire Blob bytes (not CDP's possibly absent `postDataBuffer`) and computes SHA-256 outside the page that must actually reload. An independent binary transport preflight runs before recording. Post-reload pending custody must still match the exact ID, byte length and hash. No disarm, fake stop result, capture hold, safety override or swallowed navigation error is used. Browser execution and two-shell/two-skin review remain parent-admitted acceptance gates, not claims from the source tests.

## Safety-review adjudication
1. **Confirmed ordering bug.** Actual phone `saveDrafts` persists composer state; desktop dispatches input to save it. Neither is a recording stop, but neither should run before the post-animation safety guard. Host hooks now run after async preparation and a fresh guard, followed by another synchronous guard. `prepareReload` only flushes; `commitReload` removes frames only when reload commits. A failed flush also aborts instead of being swallowed. Tests use actual app-services preparation with a retained frame/hold/load observer, plus deterministic host busy during animation and async flush, and changed native-take identity.
2. **Confirmed same-task race.** Both failed-controller callers now compare `state.rec` to the snapshotted controller after awaiting the empty proof. Tests resolve both pending promises in the same task for double Start and Start+Stop; the next engine remains starting/recording with its hold, not detached by a stale continuation.
3. **Confirmed recoverable app/shell gap, bounded ownership repair.** The verified frame facade scopes current/pending to its app ID; `resumeId` rebinds the shell session and rejects a still-starting session, rather than launching a second mic. Empty failed controllers reuse reattachment without releasing their hold; Retry adopts and Stop then saves that exact adopted take. Recorder Start supplies `meta.meetingId`. Legacy missing metadata is accepted only with an exact persisted capture-ID hint; missing or mismatched ownership stays retained with an explicit error, never guessed from the selected meeting. Concurrent adoption and stale Stop continuations are identity-fenced.
4. **Confirmed overly broad recovery abort.** Missing/malformed/throwing meeting status no longer prevents safe browser-row repair. Unknown native truth remains an error for reload and fresh Start. Pending safe rows remain accessible; an unknown owner with no safe result rejects rather than returning an empty array that an app could mistake for empty-custody proof. No unknown status is converted into native quiet.
5. **Not a bug in the current callees.** `start` consumes a warm preparation from the map synchronously and transfers its inputs to the session before awaiting. `discardPrepared` is a no-op once that entry is consumed. The regression executes the actual production consumption/release path and proves neither context close nor track stop occurs after a late setup failure.
6. **Hardening accepted.** The existing microphone lock is non-queuing for recovery; overlapping attempts could receive busy rather than serialize. Reload reconciliation now shares one in-flight promise, including after the UI timeout, until recovery settles. It does not cancel or expire the underlying operation.
7. **Confirmed stale snapshot window.** Recovery rereads native status after row I/O. A newly started native owner that has not been positively adopted blocks reload; it cannot inherit the earlier idle result. Device `recActive` remains freshly read by the synchronous predicate.

Focused source-only tests are not browser acceptance. The immutable forum worker must run the full shell suite, Recorder custody tests, exact old-source negative oracle, final-source-only positive browser replay and the two-shell/two-skin retained-audio checks. No deployment or handset repair is claimed before that gate.
